# 数据模型驱动（Data-Model-First）

> 一句话：先把数据结构定死，界面只是数据的不同投影——任何界面需求先翻译成数据问题。

---

## R — 原文（Reading）

> 数据模型驱动：先定义数据源和数据结构，再用区块展示数据，最后用操作处理数据——界面与数据彻底解耦
>
> — 《NocoBase 官方文档（中文版）》, `tutorials/v2/01-getting-started.md`

---

## I — 方法论骨架（Interpretation）

NocoBase 强制把「数据」和「呈现」分成两件事。Collection / Field / 关系构成唯一事实源，页面区块只是它的一个投影。因此任何界面需求都要先翻译成数据问题：需要哪些表、哪些字段、什么关联、什么约束。顺序一旦反过来（先拖页面再想数据），后期必然返工。

---

## A1 — 素材中的应用（Past Application）

v2 教程（极简 IT 工单系统）把「建模」和「搭页面」拆成第 2、3 两章，明确说「数据模型是系统的地基：先想清楚要存哪些数据、数据之间有什么关系，后面搭界面、配权限才能水到渠成」。AI 搭建侧同样把 nocobase-data-modeling 排在 nocobase-ui-builder 之前。

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个能力？

1. 客户只说「我要一个客户管理页」时，你应该先产出数据模型而不是先拖页面
2. 接手别人搭了一半的 NocoBase 项目时，先读数据模型再读页面
3. 发现某个需求实现不了，第一反应是回头检查数据模型是否缺字段/缺关系。

### 语言信号（用户话里出现这些就应激活）

- 「我要一个客户管理页」（需求只给界面、不给数据）
- 「这个系统从哪开始搭」（多页面的新系统）
- 「别人搭了一半，我先看什么」（接手项目）
- 某个需求怎么都实现不了（该回头查模型）

### 与相邻能力的区分

- 与 `collection-relation-choice` 的区别：本能力回答「有哪些表、哪些字段、什么约束」，表类型与关系选型回答「关系怎么连、用哪种表」——前者是顺序，后者是判据。
- 与 `main-vs-external-datasource` 的区别：本能力假设你要新建模型；若模型已在别的系统里，先走主库/外部库决策再看本能力。

## E — 可执行步骤（Execution）

1. **用一段业务语言描述需求，列 3–7 个核心业务对象（客户/订单/工单……）**
   - 完成标准：得到 3–7 个核心业务对象的清单，且能用一句话说清每个对象是什么。

2. **为每个对象列字段与关系，先写在纸上，别急着点界面**
   - 完成标准：每个对象都有字段清单与关系清单，且没有「先放着、回头再说」的字段。

3. **进「数据源管理 → 主数据源」建 Collection；无特殊结构一律用普通表**
   - 完成标准：表已在数据源管理里建好，且没有为「结构稳定、需要频繁筛选」的字段使用 JSON 兜底。

4. **关系字段先按业务语义定方向与基数，再选关系类型**
   - 完成标准：每条关系都有明确方向与基数，且业务方能用自己的话复述一遍。

5. **数据模型成型后才建页面、表单、工作流**
   - 完成标准：页面、表单、工作流只在数据模型定稿之后才开始搭建。

6. **回头做一次体检：是否存在「为了界面方便而塞进 JSON 的稳定字段」——有就拆成明确字段**
   - 完成标准：体检有明确结论：要么确认无 JSON 兜底字段，要么已列出待拆字段清单。

## B — 边界（Boundary）★

### 不要在以下情况使用此能力

- 不适用于「只为接管一个已有外部库做增删改查」的场景——此时模型已经在别处，你只做映射。
- 不适用于纯展示型数据看板——数据已在外部系统产生，你不需要新建模型。

### 素材中警告的失败模式

- **先拖页面再想数据** → 后果：界面与数据结构互相迁就，后期大改；正确做法：先出数据模型，界面只是投影

### 容易混淆的邻近方法论

- `collection-relation-choice`：本能力回答「有哪些表、哪些字段、什么约束」，表类型与关系选型回答「关系怎么连、用哪种表」——前者是顺序，后者是判据。
- `main-vs-external-datasource`：本能力假设你要新建模型；若模型已在别的系统里，先走主库/外部库决策再看本能力。
