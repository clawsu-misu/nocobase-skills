# 触发器选型矩阵（事件时序模型）

> 一句话：先定位事件在时序的哪个点，再选触发器——拦截用前、用户操作用后、数据变动用表事件。

---

## R — 原文（Reading）

> 在 NocoBase 对未来的设计中，可能会扩展更多可用于触发的操作后事件，所以更推荐使用操作后事件来处理用户操作导致数据变动的流程。
>
> — 《NocoBase 官方文档（中文版）》, `workflow/triggers/post-action.md`

---

## I — 方法论骨架（Interpretation）

把事件画成一条时间轴：操作前事件（可拦截请求）→ 执行操作 → 操作后事件（面向用户操作，带用户信息，可局部绑定按钮）/ 数据表事件（面向数据变动，更底层，无用户信息，可连锁）。外加三类独立入口：定时任务、Webhook、审批。选型先问三个问题：谁触发？能不能拦截？需不需要用户信息？

---

## A1 — 素材中的应用（Past Application）

会议室时间冲突用「操作前事件」拦截提交（tutorials/v1/13）；费用报销按金额分流用「操作后事件」（post-action.md）；下单扣库存用「数据表事件 + 预加载商品」（collection.md）；样品送检用「自定义操作事件 + 响应消息」。

---

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个能力？

1. 任何「当 X 发生时自动做 Y」的需求，先定位事件时序再动手
2. 发现工作流在 SQL 节点后不触发时，想到「SQL 直接落库绕过 ORM」
3. 设计者要求「超时未支付自动取消订单」时，直接走定时任务的数据表时间字段模式，不要自己算 30 分钟前的时间。

### 语言信号（用户话里出现这些就应激活）

- 「当订单创建后自动发通知」（该选哪个触发器）
- 「想让它每天凌晨跑一次」
- 「超时未支付自动取消订单」
- 「工作流配了但没触发」

### 与相邻能力的区分

- 与 `four-layer-permission-funnel` 的区别：触发器决定「什么时候跑」，权限决定「能碰到哪些数据」；工作流也会受数据范围约束。
- 与 `revision-checkpoint` 的区别：工作流改坏了要能回退——触发器选对不等于改动可控。

### 同一来源内的相关能力

- depends-on：`data-model-first`
- contrasts-with：—
- composes-with：`four-layer-permission-funnel`

## E — 可执行步骤（Execution）

1. **问：这是「拦截」还是「事后处理」？拦截 → 操作前事件**
   - 完成标准：已判定该需求属于「拦截」还是「事后处理」。

2. **问：由用户点击/提交引发？→ 操作后事件或自定义操作事件；由任何数据变动引发？→ 数据表事件**
   - 完成标准：已判定触发源属于：用户操作 / 数据变动 / 时间 / 外部推送 / 人工审批 之一。

3. **问：时间驱动？→ 定时任务（优先用「数据表时间字段」模式）；外部系统推送？→ Webhook；人工审批？→ 审批**
   - 完成标准：触发器已选定，且能说明「为什么不是另外几个候选」。

4. **再定执行模式：默认异步；需要即时反馈用同步（注意同步模式不能用会产生「等待」的节点）**
   - 完成标准：执行模式已确定，并检查过是否存在不能用同步模式的节点。

5. **最后排列节点链：条件判断 → 数据操作 → 通知/HTTP/人工处理**
   - 完成标准：节点链已排出：条件判断 → 数据操作 → 通知 / HTTP / 人工处理。

---

## B — 边界（Boundary）★

### 不要在以下情况使用此能力

- SQL 操作节点不触发数据表事件（直接落库绕过 ORM）；数据表事件不支持批量操作，对多关系/中间表不触发。
- 定时任务在应用停机期间错过的触发不会补触发。
- 已触发过的工作流配置变只读，必须先「复制到新版本」；全局超时只适合兜底保护，不承载业务分支。

### 容易混淆的邻近方法论

- `four-layer-permission-funnel`：触发器决定「什么时候跑」，权限决定「能碰到哪些数据」；工作流也会受数据范围约束。
- `revision-checkpoint`：工作流改坏了要能回退——触发器选对不等于改动可控。
