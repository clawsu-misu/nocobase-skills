# 三空间模型（Portal vs App vs Space）

> 一句话：多工作区解决入口、多应用解决拆分、多空间解决隔离——别混用。

---

## R — 原文（Reading）

> 多工作区解决入口问题，多应用解决系统拆分问题，多空间解决数据隔离问题。
>
> — 《NocoBase 官方文档（中文版）》, `multi-app/multi-app-vs-multi-portal-vs-multi-space.md`

---

## I — 方法论骨架（Interpretation）

三种「多」各管一件事，按需求选：入口 → 多工作区（同一应用多个访问入口，各自页面/菜单/导航/权限，共享数据与插件）；系统拆分 → 多应用（物理隔离的多个实例，独立数据库连接、独立插件配置、独立升级维护）；数据隔离 → 多空间（单实例内逻辑隔离，含空间字段的表自动按当前空间过滤）。

---

## A1 — 素材中的应用（Past Application）

多门店数据隔离用多空间（老数据通过「未分配空间」逐步归类）；单应用臃肿时按 CRM / 工单 / 资产拆多应用，各自独立「开发→预发布→生产」链路；同一系统给内部与外部两套入口用多工作区；多应用按「单应用 → 共享内存多应用 → 多环境混合部署」三阶段演进。

---

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个能力？

1. 客户说「要给几家分公司用同一套系统但数据要分开」→ 多空间，不是多应用
2. 客户说「想给经销商一个只看到部分功能的入口」→ 多工作区
3. 客户说「这套系统太臃肿了，改一个模块影响一堆」→ 多应用拆分的信号。

### 语言信号（用户话里出现这些就应激活）

- 「几家分公司用同一套系统但数据要分开」
- 「想给经销商一个只看到部分功能的入口」
- 「系统太臃肿了，改一个模块影响一堆」
- 「多应用和多空间有什么区别」

### 与相邻能力的区分

- 与 `t-shaped-data-architecture` 的区别：先决定「内容怎么扩展」（T 型），再决定「实例怎么隔离」（三空间）。
- 与 `migration-version-backup` 的区别：三空间是架构选择，本能力不负责发布链路。

### 同一来源内的相关能力

- depends-on：`t-shaped-data-architecture`
- contrasts-with：—
- composes-with：`migration-version-backup`

## E — 可执行步骤（Execution）

1. **先判定需求属于哪一类：入口 / 拆分 / 隔离**
   - 完成标准：需求已归入「入口 / 拆分 / 隔离」三者之一，没有混着做。

2. **隔离需求 → 多空间：给相关表加空间字段，系统自动按空间过滤**
   - 完成标准：隔离需求已给相关表加空间字段，并确认系统按空间自动过滤。

3. **入口需求 → 多工作区：独立页面、菜单、导航、布局、权限**
   - 完成标准：入口需求已配独立页面、菜单、导航、布局与权限。

4. **拆分需求 → 多应用：为每个应用配独立域名与独立 JWT 密钥**
   - 完成标准：拆分需求已配独立域名与独立 JWT 密钥。

5. **按规模演进：单应用 → 共享内存多应用 → 多环境混合部署（Supervisor + Worker）**
   - 完成标准：演进路径已选定（单应用 / 共享内存多应用 / 多环境混合部署）。

---

## B — 边界（Boundary）★

### 不要在以下情况使用此能力

- 多应用不配独立 JWT 密钥时，用户 ID 重复可能导致越权访问其他应用数据。
- 集群模式下数据库暂时只支持单节点；Worker ID 范围 0–31，即同一应用最多 32 个节点。
- 跨可用区、跨地域容灾需自建多集群并自行做数据复制与切换。

### 容易混淆的邻近方法论

- `t-shaped-data-architecture`：先决定「内容怎么扩展」（T 型），再决定「实例怎么隔离」（三空间）。
- `migration-version-backup`：三空间是架构选择，本能力不负责发布链路。
