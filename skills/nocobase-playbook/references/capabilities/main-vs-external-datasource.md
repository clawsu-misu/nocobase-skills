# 主库与外部库选型（Main vs External Data Source）

> 一句话：新建系统用主库，接管他系统库用外部库——一句话决策。

---

## R — 原文（Reading）

> 如果是使用 NocoBase 搭建全新的业务系统，请使用主数据库，这将可以使用 NocoBase 完整的功能。如果是使用 NocoBase 来接入其他系统的数据库实现基础的数据增删改查，则使用外部数据库。
>
> — 《NocoBase 官方文档（中文版）》, `data-sources/data-modeling/main-vs-external-data-sources.md`

---

## I — 方法论骨架（Interpretation）

先用一句话决定方向（全新系统→主库；接管他系统库→外部库），再用四个维度复核：数据库类型支持、数据表类型支持、字段类型支持、备份还原迁移能力。外部库的价值是「不改原库结构补一层管理界面」，代价是只能用普通表和视图表，且失去内建备份迁移。

---

## A1 — 素材中的应用（Past Application）

老 ERP / MES / WMS 接入：连接外部数据库 → 读取表与字段 → 配字段映射与关系元数据 → 用 NocoBase 搭管理界面、权限、工作流、报表（data-source-manager/external-database.md）。

---

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个能力？

1. 客户说「我们已经有 ERP 了，想在上面加个管理界面」→ 外部库
2. 客户说「想新做一套业务系统」→ 主库
3. 客户数据在 ClickHouse / Doris 里 → 只读分析源，不要配增删改。

### 语言信号（用户话里出现这些就应激活）

- 「我们已经有 ERP 了，想在上面加个管理界面」
- 「想新做一套业务系统」
- 「数据在 ClickHouse 里，想做成报表」
- 「接了外部库之后有些功能不能用」（选型代价）

### 与相邻能力的区分

- 与 `data-model-first` 的区别：本能力决定「表建在哪一侧」，不决定建哪些表。
- 与 `collection-relation-choice` 的区别：本能力决定数据源类型，表类型选型在数据源确定之后。

### 同一来源内的相关能力

- depends-on：`data-model-first`
- contrasts-with：`collection-relation-choice`

## E — 可执行步骤（Execution）

1. **问一句：这套系统是不是全新的？是→主库；否→外部库**
   - 完成标准：已明确回答「是不是全新系统」，并据此选定主库或外部库。

2. **外部库只接入当前应用会用到的表和视图（单数据源上限 500 张）**
   - 完成标准：外部接入的表 / 视图清单已收敛到当前应用实际用到的范围。

3. **外部库需要数据库级外键约束时，先在数据库侧建好，再回 NocoBase 同步配置**
   - 完成标准：需要外键约束的外部库已在数据库侧建好约束并完成同步配置。

4. **分析型引擎（ClickHouse/Doris）按只读分析源使用，不配写入操作**
   - 完成标准：分析型引擎仅按只读使用，未配置任何写入操作。

5. **外部库场景提前规划备份——NocoBase 不替你备份它**
   - 完成标准：外部库的备份责任人、备份频率已写明（明确由谁负责，不能默认系统管）。

---

## B — 边界（Boundary）★

### 不要在以下情况使用此能力

- 外部库不支持继承表、文件表、评论表、日历表、表达式表、树表、SQL 表，也不支持中国行政区、附件、创建人等字段。
- 外部库新增字段只保存关系元数据，不会自动建真实外键、索引或中间表。
- 外部 NocoBase 数据源需单独准备 API key 并只授予必要权限；当前应用有权限但操作失败通常是远端 key 权限不足。

### 容易混淆的邻近方法论

- `data-model-first`：本能力决定「表建在哪一侧」，不决定建哪些表。
- `collection-relation-choice`：本能力决定数据源类型，表类型选型在数据源确定之后。
