# 迁移 / 版本 / 备份 三机制不可替代（Migration vs Version vs Backup）

> 一句话：跨环境发布用迁移、开发回退用版本、容灾还原用备份——三者不能互相顶替。

---

## R — 原文（Reading）

> 发布管理用于规范应用从开发到生产的交付过程。它关注的不是单次操作，而是一套可重复、可验证、可回退的发布机制。
>
> — 《NocoBase 官方文档（中文版）》, `ops-management/release-management/index.md`

---

## I — 方法论骨架（Interpretation）

三件事各司其职：迁移管理 = 跨环境发布配置与结构（差异化更新）；版本控制 = 开发期回退节点；备份管理 = 运行态全量备份与容灾。最常见的错误是把「备份还原」当发布手段，或者把「版本」当备份用。正确链路是：开发环境搭好 → 存版本 → 发布前备份 → 生成迁移文件 → 预发布验证 → 同一份文件上生产。

---

## A1 — 素材中的应用（Past Application）

蓝绿切换发布：Staging 生成迁移文件 → PROD-A 全量备份 → PROD-B 空库部署目标版本 → 还原备份并在 PROD-B 执行迁移 → 详细测试 → 网关切流量，出问题瞬间切回 PROD-A。内网/离线交付：外网建项目装依赖打包（排除 .env）→ 拷入内网 → 补 .env → install。

---

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个能力？

1. 客户问「我改了配置怎么同步到生产」→ 迁移管理，不是备份还原
2. 客户问「系统被我改坏了怎么回去」→ 版本控制
3. 客户问「数据库炸了怎么办」→ 备份管理。三个问题三个答案。

### 语言信号（用户话里出现这些就应激活）

- 「我改了配置怎么同步到生产」
- 「系统被我改坏了怎么回去」
- 「数据库炸了怎么办」
- 「上线前要检查什么」

### 与相邻能力的区分

- 与 `revision-checkpoint` 的区别：版本节点是「开发期节奏」，本能力回答「三个机制各管一段，别用一个顶三个」。
- 与 `portal-app-space-model` 的区别：本能力管发布链路，三空间模型管多租户/多入口的架构选择。

### 同一来源内的相关能力

- depends-on：`revision-checkpoint`
- contrasts-with：—
- composes-with：`portal-app-space-model`

## E — 可执行步骤（Execution）

1. **开发环境搭好 → 存版本节点**
   - 完成标准：开发环境已有版本节点作为基线。

2. **用「变量与密钥」提前隔离环境相关配置（数据库连接、第三方地址、Token、Webhook），不写死在页面或工作流里**
   - 完成标准：环境相关配置全部收敛到「变量与密钥」，页面与工作流里无明文。

3. **规划「开发 → 预发布 → 生产」三段链路**
   - 完成标准：「开发 → 预发布 → 生产」三段链路已明确写下来。

4. **发布前做发布前备份，且备份必须覆盖数据库 + 用户上传文件 + 应用运行所需存储**
   - 完成标准：发布前备份已执行，且覆盖数据库 + 用户上传文件 + 应用运行所需存储。

5. **从开发环境生成迁移文件；先在预发布验证，验证通过的同一份文件用于生产，不得临时修改**
   - 完成标准：迁移文件已生成并在预发布环境验证通过，生产使用同一份文件、未临时修改。

6. **迁移规则：内置表默认「覆盖」，用户自定义业务表选「仅结构」以免覆盖生产数据**
   - 完成标准：迁移规则已确认：内置表覆盖、用户自定义业务表选「仅结构」。

7. **发布窗口内停止用户访问；集群先缩容到单节点，完成后再恢复**
   - 完成标准：发布窗口已安排；集群先缩容到单节点再发布。

8. **发布失败优先用发布前备份还原；恢复前先给当前状态也做一份备份**
   - 完成标准：回退路径已明确（优先用发布前备份还原），且回退前已备份当前状态。

## B — 边界（Boundary）★

### 不要在以下情况使用此能力

- 迁移只处理主数据库中的应用配置与结构，不迁移外部数据库和子应用数据。
- storage 目录中的部分数据（日志、备份历史、请求日志）不会自动迁移；密钥文件（aes_key.dat / jwt_secret.dat）必须一并迁移，否则加密数据无法解密、token 失效。
- 集群下插件安装/升级/备份/恢复/迁移必须缩容至单节点执行。

### 素材中警告的失败模式

- **用「备份还原」当发布手段** → 后果：覆盖生产数据，且无法回滚；正确做法：发布走迁移管理，回滚走备份管理
- **生产用 IP:port 长期对外** → 后果：cookie 不按端口隔离，登录态互相覆盖；正确做法：域名 + 反向代理 + HTTPS
- **同一配置在 CLI 与 .env 各维护一份** → 后果：排查时无法判断哪层生效；正确做法：有 CLI 参数就用 CLI，其余才写 .env

### 容易混淆的邻近方法论

- `revision-checkpoint`：版本节点是「开发期节奏」，本能力回答「三个机制各管一段，别用一个顶三个」。
- `portal-app-space-model`：本能力管发布链路，三空间模型管多租户/多入口的架构选择。
